# テキストを生成しないAI「Jev」にテトリスじゃなくズーキーパーを解かせて、Haiku 4.5と殴り合わせた

## まずこれを見てほしい

![jevとHaiku 4.5を同時に走らせた画面](★ここにjev_vs_haiku.gifをアップロード★)

左が **Jev**、右が **Claude Haiku 4.5**。

条件は徹底的に揃えてあります。

- **同じパズル** — 同じseedから作った同一の盤面。スタート直後に左右へ同じ盤面が出るので目で確認できる
- **同じ候補手・同じラベル** — 絞り込みもシャッフルも共通コード
- **同じ手数** — 30手固定。「先に目標へ着いた方が止まる」という不公平をなくしている
- **同じ経路** — 同じゲートウェイ、同じコード、同じ計測系
- **同時スタート** — 別スレッドで並走

違うのは「どの手が最善か」を誰に聞くかだけ。

同じ30手を終えた時点がこれ。

| | Jev | Haiku 4.5 |
|---|---|---|
| レイテンシ中央値 | **727 ms** | 3,495 ms |
| 使用トークン | 30,774 / 3,022 | 24,489 / 5,493 |
| かかったお金 | **$0.0043** | $0.0520 |

**同じ回数考えさせて、12倍の価格差。** 動画では、Jevがぽんぽん打っていく横でHaikuがじっくり考えているのが見えます。

これが言いたいことのほぼ全部で、以下はその裏取りです。

## Jevとは

[TypeSafe AI](https://docs.typesafe.ai/) の **System One** というモデル。一言でいうと **テキストを生成しないAI** です。

普通のLLMはトークンを1個ずつ吐き出しますが、Jevは違う。状態と「型のついた質問」を渡すと、**確率つきの答え**が返ってくる。

質問の型は3つ。

- `choice` — 選択肢から1つ選ぶ。各選択肢の確率と確信度つき
- `score` — 段階評価
- `noul` — 真偽の確率（yes/noを0〜1で）

コードだとこうです。

```python
from typesafe_sdk import TypeSafeClient, Choice, Noul

client = TypeSafeClient(model="typesafe/jev-latest")

res = client.system_one(
    state={"board": [...], "stats": {...}},
    questions={
        "best":   Choice(instructions="Which candidate is the best move?",
                         criteria={"A": "swap (2,3)...", "B": "swap (5,1)..."}),
        "urgent": Noul(instructions="Is the board in a bad shape?"),
    },
)

res.choices["best"].choice          # -> "B"
res.choices["best"].probabilities   # -> {"A": 0.12, "B": 0.71, ...}
res.choices["best"].confidence      # -> 0.83
res.nouls["urgent"].noul            # -> 0.31
```

面白いのは `probabilities` と `confidence` が付いてくること。LLMのlogprobsは基本非公開なので、「どのくらい迷ったか」が取れるのは実用上でかい。

あと **複数の質問を1往復でまとめて聞ける**。上の例も `best` と `urgent` で1リクエストです。

### どういう仕事に効くのか

逆に、Jevは文章を書けません。要約も説明も翻訳もできない。

なので「分類・選択・判定を高頻度で回す」仕事専用です。逆にいうと、**そういう仕事にLLMを使うのは、文章生成能力に金と時間を払っているだけ**かもしれない。そこを確かめたかった。

## なぜズーキーパーなのか

元ネタは [LLMとJevのテトリス比較検証](https://zenn.dev/yrd/articles/64d4e2f4c3e71c) という記事です。最初はそのままテトリスで追試しました。

でもテトリスだと**判断が問われない**。大半の局面で「穴を作らない安全な置き場所」が1つに見えていて、盤面を読まなくても当たってしまう。

そこで [ZOO KEEPER](https://ja.wikipedia.org/wiki/ZOO_KEEPER_(%E3%82%B2%E3%83%BC%E3%83%A0))（KITERETSU/ROBOT, 2003）のルールに寄せました。本家準拠にしたのはここ。

- 8×8に **7種の動物**（ゾウ・キリン・ワニ・パンダ・カバ・サル・ライオン）
- 隣接2匹を入れ替えて3匹以上並べると消える
- **入れ替えても消せない手はそもそも打てない**（候補に出てこない）
- 消えると上から落ちて連鎖する
- 捕獲でタイマーが回復し、1手ごとに減る。0でゲームオーバー
- **全種のノルマ**を満たすとレベルアップ。レベルが上がるほどタイマーが速く減る
- 手詰まりになったら盤面を総入れ替え

**ノルマが「全種いくつずつ」なのが効きます。**

ライオンのノルマが終わっていてワニが残っているなら、**ライオン6匹よりワニ3匹の手の方が価値がある**。「一番多く消える手」が正解とは限らない。素点だけで順位が決まらないので、ちゃんと判断が要る。

実際、Haikuに打たせたときの自己申告がこれ。

> 最も重要なのは最も多く動物を捕獲する手ではなく、残りノルマが最大の種を狙うことだった。対象の動物が盤面にない手番では、打てる手数を温存して待った。

狙いどおりの判断をしている。

## ゲームをどう操作させたか

ここが一番の工夫どころでした。

### 「盤面を渡して自由に指させる」はやらない

LLMに生の盤面を渡して「どう動かす?」と聞くと、座標の書式がぶれるし、そもそも非合法手を返してくる。パースと検証で消耗するし、**モデルの判断力ではなく出力形式の安定性を測ることになってしまう**。

なので **合法手をこちらで全部列挙して、ラベルを振って選ばせる** 形にしました。

### 1手の流れ

1. 現在の盤面で **打てる手を全部列挙** する（隣接ペア112通りを総当たり）
2. ヒューリスティック評価式で **上位12手に絞る**
3. **順番をシャッフルしてから** `A`〜`L` のラベルを振る
4. 「どれが最善か」を1回だけ聞く
5. 返ってきたラベルの手を打つ

評価式はこれ。

```
score = 2.0 × (まだ足りない動物を消す数)
      + 0.4 × (ノルマ達成済みの動物を消す数)
      + 3.0 × (連鎖 - 1)
      + 2.0 × (最長の直線 - 3)
      + 0.3 × (打てる手の増減)
```

### シャッフルが必須な理由

**3のシャッフルをサボると計測が壊れます。**

評価値順にラベルを振ると、ラベル`A`が常に最善手になる。すると盤面を1ミリも読まずに「A」と答えるだけで正解でき、位置バイアスだけで高得点が出てしまう。

評価順は内部に保持したまま、モデルに見せる順番だけ毎手シャッフルしています。

### モデルに渡している内容

```
Board: ["EGCPHMLE", "GCPHMLEG", ...]
Stats: {"level": 2, "score": 1070, "timer": 84.4,
        "still_needed": {"elephant": 6, "lion": 2}, "moves_available": 9}
Candidates:
  A: swap (2,3)<->(2,4): catches 3x panda; 1 cascade(s), longest line 3, 7 moves left after
  B: swap (5,1)<->(6,1): catches 4x lion; 2 cascade(s), longest line 4, 5 moves left after
  ...
```

Jevには `criteria` として、Haikuには同じ内容をプロンプトとして渡します。**両者が見る情報は完全に同じ**。

### 公平にするためにやったこと

- **同じseed** — 初期盤面もミノ列も乱数も全部同じ
- **同じ候補手・同じラベル** — 評価も絞り込みもシャッフルも共通コード
- **同じゲートウェイ** — 両方とも[ロリポップ！AIゲートウェイ](https://ai-gateway.lolipop.jp/)経由。キー1本でJevもClaudeも叩ける
- **API失敗時はヒューリスティックで代打ちし、その手数を記録** — 後述

## 結果

**30手固定**にして、同じ局面から何点取れるかで比較しました（seed 0〜4）。

| | score平均 | score範囲 | レイテンシ/手 | コスト/局 |
|---|---|---|---|---|
| **Jev** | **2,644** | 2,360〜2,860 | **442 ms** | **$0.0041** |
| Haiku 4.5 | 2,578 | 2,130〜3,120 | 2,583 ms | $0.0453 |
| ヒューリスティック | 2,552 | 1,890〜3,150 | 0 ms | $0 |

**Jevは5.8倍速く、11倍安い。スコアはほぼ同じ。**

元記事は「約4倍速・約1/24のコスト・品質はほぼ同等」でしたが、方向も桁も一致しました。

### ただしスコア差は「差がない」と読むべき

2,644 対 2,578 で一見Jevが勝っていますが、**seedごとの標準偏差がJev 192・Haiku 444**。差(66)より遥かに大きい。

つまり **判断の質に有意差があるとは言えない**。5 seedでは足りません。

はっきり差が出たのは速度とコストの方で、こちらはseed依存が小さいので5 seedでも言えます。

## ハマったところ

### ゲートウェイが構造化出力を黙って無視する

Haiku側は最初 `output_config` でJSON Schemaのenumに固定していました。ところが**30手中30手フォールバック**。

調べたらゲートウェイが `output_config` を受け取って **エラーも返さず200で、スキーマを完全に無視**していた。返ってきたのはただの散文です。

```
stop_reason: end_turn
text: "I'd be happy to help, but I don't see the options for A, B, and C..."
```

400が返れば即わかったのに、200で黙って無視されるのが一番たちが悪い。

### 一番危なかったのは「静かに成功して見える失敗」

API失敗時はヒューリスティック最善手で代打ちして局を止めない設計にしていました。これ自体は妥当なんですが、**全手フォールバックすると成績が満点に見える**。

ヒューリスティックとの一致率100%、評価値との差0.00。**それはヒューリスティックの成績であって、そのエージェントの成績ではない。**

このプロジェクトでは実際に2回、誤ったデータを作りかけました。

1. 上記の構造化出力の件(30/30手)
2. サブエージェントがレート制限で死んだまま20分走り続けた件(8/14手)

2番目は `agreement 0.93 / mean_regret 0.04` という **一見とても優秀な行** が出来上がっていて、危うく信じるところでした。

対策として **フォールバック手数を必ず結果表に出す**ようにして、0でない行は「測れていない」と明示しています。連続2手無応答なら局ごと中止して、結果行自体を出さないようにもしました。

### 評価式が嘘の数字をモデルに見せていた

候補手の説明に `moves left after 93` みたいな値が頻出するのが不自然で、調べたら **予測と実際の相関 r = 0.069**（予測平均41手に対し実際8.4手）。ほぼ無相関でした。

原因は2段階。

- 候補評価用の盤面は「補充なし」で作るので、1連鎖で止まって**消え残りの並びが盤面に残る**
- 合法手の判定を「盤面のどこかに並びがあるか」でやっていたので、その残骸のせいで**ほぼ全ペアが合法手に化けていた**

判定を「**入れ替えた2マス自身が並びを作るか**」に直したら **r = 0.900** になりました。

これは評価式が雑音を拾っていただけでなく、**`moves_after` は候補説明としてJevにもHaikuにもそのまま渡している数字**なので、両モデルに嘘を見せていたことになります。

## 指標の話（これが一番の学び）

「ヒューリスティック最善手との一致率」や「評価値の差」を品質指標にしようとしたんですが、**これは間違いでした**。

データがそれを否定しました。

- ヒューリスティックは定義上、一致率100%・評価値差0.00
- しかし30手スコアは3者で**最下位**

つまりこれらは **「評価式への追従度」** を測っているだけで、評価式そのものが正解じゃない以上、品質の指標にはならない。

さらに、**指標によって順位が逆転**します。

| | 30手固定スコア | レベル2到達までの手数 |
|---|---|---|
| Jev | ヒューリスティックをやや下回る | ヒューリスティックを上回る(19.0 対 20.2) |

30手固定はノルマ進行が報われない純粋な点取りになるので、点取りに最適化された評価式が有利になる。**どちらか一方で優劣は言えない**ので、両方載せることにしました。

## まとめ

- **テキストを生成する能力が要らない仕事に、LLMを使うのは高くて遅い**。1手200ms級の選択をゲームループで回すなら、System Oneのようなモデルの方が筋がいい
- 今回の実測では **5.8倍速・11倍安・スコアは有意差なし**
- ただし **スコア差を語るには5 seedでは全然足りない**。速度とコストの差は明確
- 計測系を作るときは **「静かに成功して見える失敗」を検知する仕組み**を先に入れること。フォールバックは局を止めないために必要だが、それを可視化しないと嘘のデータが出来上がる

コードは全部ここに置いてあります（ズーキーパーとテトリス、4種のエージェント、ブラウザで左右比較できるビューア）。
