# テキストを生成しないモデル Jev で Claude Haiku 4.5 を置き換えられるか測ってみる

分類や選択にしか使っていない LLM がある。
返ってくるのは `A` の一文字なのに、文章を生成するモデルに毎回トークンを吐かせている。
この用途なら、文章を生成しないモデルのほうが速くて安いはずである。

TypeSafe AI の System One（Jev）がその種類のモデルである。
状態と選択肢を渡すと、文章ではなく、選択肢ごとの確率と確信度が直接返ってくる。
トークンを 1 つずつ生成しないので、出力の長さに比例した時間と費用がかからない。

どれだけ差が出るかを測ってみた。
題材はよくある 3 マッチパズルにして、候補手 12 個から最善手を選ばせる処理を 30 手 × 5 局まわした。

左が Jev、右が Claude Haiku 4.5 である。
同じ盤面を渡して、30 手ずつ打たせている。

結果を先に書くと、Jev は Haiku の 3.1 分の 1 の時間と 10.7 分の 1 の費用で動いた。
ただしスコアには差が出なかった。
API を一度も呼ばないヒューリスティックが両者の中間に入ってしまったので、判断の質を比較できたとは言えない。

## Jev の API と返り値

System One に渡すのは、状態と「型のついた質問」である。
返ってくるのは、選択肢ごとの確率と確信度になる。

質問の型は 3 つある。
選択肢から 1 つ選ぶ `choice`、段階評価を返す `score`、真偽を 0 から 1 の確率で返す `noul` である。

```python
# typesafe-sdk / Python 3.10.12
from typesafe_sdk import TypeSafeClient, Choice, Noul

client = TypeSafeClient(model="typesafe/jev-latest")

res = client.system_one(
    state={"board": [...], "stats": {...}},
    questions={
        "best":   Choice(instructions="Which candidate is the best move?",
                         criteria={"A": "swap (2,3)...", "B": "swap (5,1)..."}),
        "urgent": Noul(instructions="Is the board in a bad shape?"),
    },
)

res.choices["best"].choice          # -> "B"
res.choices["best"].probabilities   # -> {"A": 0.12, "B": 0.71, ...}
res.choices["best"].confidence      # -> 0.83
res.nouls["urgent"].noul            # -> 0.31
```

`probabilities` と `confidence` が付くのが、LLM を使う場合との違いである。
LLM の logprobs は多くの提供形態で取得できないので、どの程度きわどい選択だったのかを呼び出し側で判定できない。
上の例のように複数の質問を 1 リクエストにまとめられるため、状態の送信も 1 度で済む。

その代わり、System One は文章を返さない。
要約も説明も翻訳もできず、答えられるのは渡した選択肢のどれかである。
選択肢をこちらで用意できる処理にしか使えない。

## 題材にしたパズル

よくある 3 マッチパズルを実装した。
ルールは次のとおりである。

- 8×8 の盤面に 7 種の動物（ゾウ・キリン・ワニ・パンダ・カバ・サル・ライオン）を置く
- 隣接する 2 匹を入れ替え、縦か横に 3 匹以上並ぶと消える
- 入れ替えても何も消せない手は、そもそも選べない
- 消えた場所には上から動物が落ちてきて、連鎖が起きることがある
- 動物を捕獲するとタイマーが回復し、1 手ごとに減る。0 になるとゲームオーバー
- 全種のノルマを満たすとレベルが上がり、レベルが上がるほどタイマーの減りが速くなる
- どう動かしても消せない配置になったら、盤面を総入れ替えする

この題材を選んだのは、ノルマが種ごとに課されるからである。
ライオンのノルマが埋まっていてワニが残っているなら、ライオンを 6 匹消す手よりワニを 3 匹消す手のほうがレベルアップに近づく。
捕獲数の多い手が常に最善とは限らないので、素点の大小だけでは順位が決まらない。
モデルに聞く意味のある局面が残る、と考えた。

動画の緑のバーはタイマーである。
手番制なので、実時間ではなく 1 手ごとに一定量を減らしている。
レベル 1 では 1 手あたり 6.0 減り、捕獲 1 匹につき 1.6 回復する。

## 計測の前提

### 盤面ではなく候補手を渡す

盤面をそのまま渡して「どう動かすか」を自由に答えさせる形は採らなかった。
座標の書き方が揺れるうえ、入れ替えても何も消せない非合法手が返ってくる。
パースと再試行の実装が増えるだけでなく、測っている対象が判断の質ではなく出力形式の安定性にすり替わる。

代わりに、合法手をこちらで列挙してラベルを振り、そこから選ばせる形にした。
1 手の処理はこう進む。

1. 現在の盤面で打てる手を列挙する（隣接ペア 112 通りを総当たり）
2. ヒューリスティック評価式で上位 12 手に絞る
3. 順番をシャッフルしてから `A` から `L` のラベルを振る
4. どれが最善かを 1 回だけ尋ねる
5. 返ってきたラベルの手を打つ

2 で使う評価式はこれである。

```
score = 2.0 × (まだノルマが残っている動物を消す数)
      + 0.4 × (ノルマ達成済みの動物を消す数)
      + 3.0 × (連鎖数 - 1)
      + 2.0 × (最長の直線 - 3)
      + 0.3 × (打てる手の増減)
```

3 のシャッフルを省くと、計測そのものが成立しない。
評価値の高い順にラベルを振ると `A` が常に評価式の最善手になる。
盤面を読まずに `A` と答えるだけで評価式と一致してしまい、位置の偏りだけで高得点が出る。
評価順は内部で保持したまま、モデルに見せる順番だけを毎手シャッフルしている。

モデルに渡しているのは、盤面と統計と候補手の一覧である。

```
Board: ["EGCPHMLE", "GCPHMLEG", ...]
Stats: {"level": 2, "score": 1070, "timer": 84.4,
        "still_needed": {"elephant": 6, "lion": 2}, "moves_available": 9}
Candidates:
  A: swap (2,3)<->(2,4): catches 3x panda; 1 cascade(s), longest line 3, 7 moves left after
  B: swap (5,1)<->(6,1): catches 4x lion; 2 cascade(s), longest line 4, 5 moves left after
  ...
```

Jev にはこれを `criteria` として、Haiku にはプロンプトとして渡す。

### 比較した 3 つのエージェント

違うのは 4 のステップ、つまり「12 個のうちどれが最善か」を誰に聞くかだけである。

| 名前 | 誰が選ぶか | API |
|---|---|---|
| `jev` | System One に聞く | 呼ぶ |
| `claude` | Haiku 4.5 に聞く | 呼ぶ |
| `heuristic` | 誰にも聞かない。2 で使った評価式の 1 位をそのまま打つ | 呼ばない |

`heuristic` を入れたのは、モデルを呼ぶ意味があるかどうかを判定するためである。
12 手に絞る時点で評価式はすでに順位を付けている。
その 1 位をそのまま打った場合のスコアを知らないと、モデルが選び直したことに意味があったのか分からない。
`heuristic` は基準線であって、比較相手ではない。

### 3 者で揃えた条件

| 項目 | 揃え方 |
|---|---|
| 初期盤面 | 同じ seed から生成した同一の盤面 |
| 候補手とラベル | 列挙・絞り込み・シャッフルとも共通コード |
| 手数 | 30 手固定 |
| 目的の説明文 | ゲーム側が持つ 1 つの文字列を、モデルに聞く 2 者へそのまま渡す |
| 通信経路 | `jev` と `claude` は同じゲートウェイ・同じ API キーを通る（次節） |

手数を固定したのは、「先にレベル 3 に到達したほうが勝ち」という形式だと到達した側だけ早く止まり、手数が揃わなくなるからである。

### 両方を同じゲートウェイから叩く

Jev と Haiku は提供元が違うので、素直にやると契約も SDK も通信先も別になる。
それでは速度差を測っても、モデルの差なのか経路の差なのか分からない。

今回は[ロリポップ！AI ゲートウェイ](https://ai-gateway.lolipop.jp/)を使った。
OpenAI 互換と Anthropic 互換のエンドポイントに加えて、System One と同じ `POST /v1/systemone` を提供している。
API キー 1 本で Jev と Claude の両方を通せる。

コード側で変えたのは、それぞれの SDK が読む base URL だけである。

```bash
# .env
TYPESAFE_API_KEY=sk-...            # ゲートウェイの推論用キー
TYPESAFE_BASE_URL=https://ai-gateway.lolipop.jp
TYPESAFE_DEFAULT_MODEL=typesafe/jev-latest

ANTHROPIC_API_KEY=sk-...           # 同じキーでよい
ANTHROPIC_BASE_URL=https://ai-gateway.lolipop.jp
JEV_LLM_MODEL=claude-haiku-4-5
```

どちらの SDK も `*_BASE_URL` を自分で読むので、呼び出しコードは書き換えていない。
費用も 1 つの残高から引かれるため、同じ基準で比べられる。

詰まった点を 2 つ書いておく。
`typesafe/jev-latest` は組織レベルで利用許可を出さないと `403 model_not_allowed` になる。
前払い式なので、残高が無いと `402 Insufficient balance` で止まる。
どちらもキーの発行だけでは解決しなかった。

### 実行環境と再現手順

2026-09-21 に計測した。
Python 3.10.12、ゲートウェイ上の Haiku は `claude-haiku-4-5`、Jev は `typesafe/jev-latest` である。

```bash
uv venv .venv
uv pip install --python .venv/bin/python -e ".[dev]"
cp .env.example .env   # ゲートウェイのキーを書く

.venv/bin/jev-bench --agent jev --agent claude --agent heuristic \
  --turns 30 --seed 0 --games 5
```

キーが無いエージェントは理由を表示してスキップされるので、`--agent heuristic` だけなら API キー無しで動く。

## スコアの差をどう読むか

スコアは 3 者の分布が重なっている。
平均だけ見れば Haiku が最も高いが、標準偏差が平均の差を上回っている。
seed 0 では Haiku が 3,310 対 2,700 で勝ち、seed 3 では Jev が 2,180 対 2,720 で負け、seed 1 と 4 では Jev が上である。
この 5 局から優劣は読み取れない。

それよりも、API を一度も呼ばないヒューリスティックが 3 者の真ん中（2,552）に入ったほうが重要な結果だった。
候補を 12 手に絞り込む時点で評価式がすでに大半の仕事を終えていて、最後の 1 個をどのモデルに選ばせても 30 手のスコアがあまり動かない、と読める。

つまり、この計測で示せたのは速度と費用の差であって、判断の質の差ではない。

## この計測で測れていないこと

- 判断の質を比較できていない。候補を 12 手に絞る評価式が強すぎて、モデルの選択がスコアに反映されにくくなっている
- 5 局では足りない。スコアの標準偏差が平均の差より大きい
- レイテンシはゲートウェイ経由の値である。直接 API を叩いた場合の値ではない
- 費用はゲートウェイの課金額をそのまま使っている。直接契約した場合の単価とは異なる
- 合法手を全列挙できる題材は、むしろ特殊な部類である。選択肢をこちらで列挙できない処理には Jev を使えない

## 測れたことと、次に試すこと

この題材に限れば、ヒューリスティックだけで解いておくのが確実だった。
API を呼ばないので失敗もせず、費用もかからず、同じ seed なら必ず同じ手を打つ。
それでスコアが 2 つのモデルと区別が付かないのだから、モデルを呼ぶ理由がない。
評価式を書き切れる問題なら、まず評価式を書くほうがよい。

そのうえで、Jev を使う場面はあると思っている。
評価式を書き切れない判断で、それでも 1 件ずつ API に聞きたいときである。
同じ選択を同じ回数させたとき、Jev は Haiku の 3.1 分の 1 の時間と 10.7 分の 1 の費用で済んだ。
速度と費用の差は seed をまたいで一貫していたので、ここは信用してよい。
精度を厳密に要求しない選択処理で、件数が多く、応答を待たせたくない場合には使えそうである。

ただし、その精度の差そのものは測れていない。
候補を 12 手に絞る評価式が強すぎて、最後の 1 手の選択がスコアにほとんど影響していない。
ベンチマークの題材選びを間違えた、というのが正直なところである。
