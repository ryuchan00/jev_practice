# テキストを生成しないモデル Jev と Claude Haiku 4.5 に同じパズルを解かせて、速度と費用と判断を比べる

TypeSafe AI の System One は、文章を生成しないモデルである。状態と型のついた質問を渡すと、選択肢ごとの確率と確信度が返る。返るのが選択肢ひとつとその確率だけなので、出力トークン数に比例する時間と費用がかからない。分類や選択だけを高い頻度で繰り返す処理なら、この形のほうが安く速く済む理屈になる。ただし、判断の質をどれだけ手放すことになるのかは、自分の題材で測らないとわからない。そこで、ズーキーパー型のマッチ 3 パズルを 30 手ずつ打たせて、System One の Jev と Claude Haiku 4.5 を並べた。

左が Jev、右が Haiku 4.5 である。両者には同じ seed から生成した同一の初期盤面を渡している。候補手の列挙、上位 12 手への絞り込み、ラベルの割り当てはすべて共通のコードが行い、通信もどちらも同じゲートウェイを経由する。手数も 30 手で揃えてある。異なるのは、その 12 手のうちどれが最善かを誰に尋ねるかだけである。

この 1 局では、Jev がレベル 3・スコア 3,810 に到達し、Haiku はレベル 2・スコア 2,840 で 30 手を終えた。1 手あたりの API レイテンシの中央値は 855 ミリ秒と 2,927 ミリ秒、1 局の費用は $0.0048 と $0.0488 だった。スコアの差については、この 1 局だけで優劣を論じることはできない。seed を 5 つに増やすと勝敗は seed ごとに入れ替わり、最後まで残るのは速度と費用の差だけになる。その計測は後の節で示す。

## System One という種類のモデル

System One に渡すのは、状態と、型のついた質問の組である。質問の型は三つあり、選択肢からひとつ選ぶ `choice`、段階評価を返す `score`、真偽を 0 から 1 の確率で返す `noul` が使える。

```python
from typesafe_sdk import TypeSafeClient, Choice, Noul

client = TypeSafeClient(model="typesafe/jev-latest")

res = client.system_one(
    state={"board": [...], "stats": {...}},
    questions={
        "best":   Choice(instructions="Which candidate is the best move?",
                         criteria={"A": "swap (2,3)...", "B": "swap (5,1)..."}),
        "urgent": Noul(instructions="Is the board in a bad shape?"),
    },
)

res.choices["best"].choice          # -> "B"
res.choices["best"].probabilities   # -> {"A": 0.12, "B": 0.71, ...}
res.choices["best"].confidence      # -> 0.83
res.nouls["urgent"].noul            # -> 0.31
```

返り値には選んだ選択肢だけでなく、選択肢ごとの確率と確信度が付く。LLM の logprobs は多くの提供形態で取得できないため、どの程度きわどい選択だったのかを呼び出し側で判定できる点は、この形式の実用上の利点である。上の例のように複数の質問を一度のリクエストにまとめられるので、状態の送信も一度で済む。

その代わり、System One は文章を返さない。要約も説明も翻訳もできず、答えられるのは渡した選択肢のどれかである。適用できるのは、選択肢をこちらで用意できる処理に限られる。

## テトリスからズーキーパーに変えた理由

この比較の出発点は、[LLM と Jev のテトリス比較検証](https://zenn.dev/yrd/articles/64d4e2f4c3e71c)という記事である。最初はそのままテトリスで追試したが、テトリスは判断の質を測る題材として向いていなかった。盤面が平らなうちは、穴を作らず高さも増やさない置き場所がほぼ一意に決まってしまい、盤面をまともに読まなくても評価式が推す手と一致する。どのモデルに聞いても同じ答えが返る局面ばかりでは、差が出ない。

そこで、[ZOO KEEPER](https://ja.wikipedia.org/wiki/ZOO_KEEPER_(%E3%82%B2%E3%83%BC%E3%83%A0))（KITERETSU / ROBOT, 2003）のルールに寄せたマッチ 3 パズルを実装した。本家に合わせたのは次の点である。

- 8×8 の盤面に 7 種の動物（ゾウ・キリン・ワニ・パンダ・カバ・サル・ライオン）を配置する
- 隣接する 2 匹を入れ替え、縦か横に 3 匹以上並ぶと消える
- 入れ替えても何も消せない手は、そもそも選べない
- 消えた場所には上から動物が落ちてきて、連鎖が起きることがある
- 動物を捕獲するとタイマーが回復し、1 手ごとに減る。0 になるとゲームオーバー
- 全種のノルマを満たすとレベルが上がり、レベルが上がるほどタイマーの減りが速くなる
- どう動かしても消せない配置になったら、盤面を総入れ替えする

ノルマが種ごとに課されるという一点が、判断の必要性を生む。ライオンのノルマが埋まっていてワニが残っているなら、ライオンを 6 匹消す手よりワニを 3 匹消す手のほうがレベルアップに近づく。捕獲数の多い手が常に最善とは限らないので、素点の大小だけでは順位が決まらない。

実際に Haiku に 30 手打たせたあと、どういう方針で選んだかを聞くと、次のように答えた。

> 最も重要なのは最も多く動物を捕獲する手ではなく、残りノルマが最大の種を狙うことだった。対象の動物が盤面にない手番では、打てる手数を温存して待った。

## 候補手を列挙してラベルで選ばせる

盤面をそのまま渡して「どう動かすか」を自由に答えさせる形は採らなかった。その形式では座標の書き方が揺れるうえ、入れ替えても何も消せない非合法手が返ってくる。パースと再試行の実装が増えるだけでなく、測っている対象が判断の質ではなく出力形式の安定性にすり替わる。

代わりに、合法手をこちらで列挙し、ラベルを振って選ばせる形にした。1 手の処理は次の順に進む。

1. 現在の盤面で打てる手を列挙する（隣接ペア 112 通りを総当たりする）
2. ヒューリスティック評価式で上位 12 手に絞る
3. 順番をシャッフルしてから `A` から `L` のラベルを振る
4. どれが最善かを 1 回だけ尋ねる
5. 返ってきたラベルの手を打つ

2 で使う評価式は次のとおりである。

```
score = 2.0 × (まだノルマが残っている動物を消す数)
      + 0.4 × (ノルマ達成済みの動物を消す数)
      + 3.0 × (連鎖数 - 1)
      + 2.0 × (最長の直線 - 3)
      + 0.3 × (打てる手の増減)
```

3 のシャッフルを省くと、計測そのものが成立しなくなる。評価値の高い順にラベルを振ると `A` が常に評価式の最善手になるため、盤面を読まずに `A` と答えるだけで評価式と一致してしまう。評価順は内部で保持したまま、モデルに見せる順番だけを毎手シャッフルしている。

モデルに渡しているのは、盤面と統計と候補手の一覧である。

```
Board: ["EGCPHMLE", "GCPHMLEG", ...]
Stats: {"level": 2, "score": 1070, "timer": 84.4,
        "still_needed": {"elephant": 6, "lion": 2}, "moves_available": 9}
Candidates:
  A: swap (2,3)<->(2,4): catches 3x panda; 1 cascade(s), longest line 3, 7 moves left after
  B: swap (5,1)<->(6,1): catches 4x lion; 2 cascade(s), longest line 4, 5 moves left after
  ...
```

Jev にはこれを `criteria` として、Haiku にはプロンプトとして渡す。ゲームの目的を説明する文もゲーム側が一箇所で持っており、両者に同じ文字列が渡る。どちらの API キーも[ロリポップ！AI ゲートウェイ](https://ai-gateway.lolipop.jp/)の同一のものを使っているので、ネットワーク経路も共通である。

## 30 手固定での計測結果

比較は 30 手で打ち切る形にした。「先にレベル 3 に到達したほうが勝ち」という形式だと、到達した側だけが早く止まって手数が揃わなくなる。同じ局面から同じ手数でどれだけ点を取れたかを見るほうが、条件を揃えやすい。seed 0 から 4 までの 5 局を、Jev、Haiku、API を呼ばないヒューリスティック単体の 3 者で走らせた。

| | スコア平均 | スコア範囲 | 標準偏差 | レイテンシ / 手 | 費用 / 局 |
|---|---|---|---|---|---|
| Jev | 2,494 | 2,180〜2,700 | 179 | 905 ms | $0.0045 |
| Haiku 4.5 | 2,676 | 2,190〜3,310 | 370 | 2,834 ms | $0.0478 |
| ヒューリスティック | 2,552 | 1,890〜3,150 | 440 | 0 ms | $0 |

速度と費用の差は、seed をまたいでも順位が変わらなかった。Jev の 1 手は Haiku の 3.1 分の 1 の時間で返り、1 局の費用は 10.7 分の 1 で済んでいる。レイテンシにはゲートウェイの往復も含まれるので、モデル単体の推論時間はこれより短い。

一方、スコアについては 3 者の分布が重なっており、この 5 局から優劣を読み取ることはできない。平均の並びだけを見れば Haiku が最も高いが、標準偏差が平均の差を上回っている。seed によっては Jev が Haiku を上回る局もある。

むしろ目を引くのは、API を一度も呼ばないヒューリスティックが 3 者の真ん中に入っていることである。候補を 12 手に絞り込む時点で評価式がすでに大半の仕事を終えており、最後の 1 個をどのモデルに選ばせても 30 手のスコアがあまり動かない、という読み方ができる。この計測で示せたのは速度と費用の差であって、判断の質の差ではない。

元記事がテトリスで報告した値は、レイテンシ中央値が 239 ミリ秒と 1,011 ミリ秒、1 局の推定費用が $0.006 と $0.15、20 ライン到達が 10 局中 8 局と 9 局だった。ゲームもモデル構成も違うので倍率をそのまま比べることはできないが、「速度と費用には大きな差があり、判断の質には差が見えない」という方向は一致した。

## 計測を壊していた不具合

ここまでの数値は、次の不具合を直したあとに取り直したものである。いずれも、エラーを出さずに計測を歪めるという共通の性質を持っていた。

### Jev 側に残っていたテトリス用の指示文

記事用に録った 1 局で、Haiku のスコアが Jev を 400 点ほど上回った。理由を探して実装を読み直すと、Jev に渡す質問文がテトリス時代のまま残っていた。

```python
INSTRUCTIONS = (
    "Which candidate placement is the best move? Prefer moves that clear lines, "
    "create no new holes, and keep the stack low and flat."
)
```

ライン消去も穴も積み上がりの高さも、ズーキーパーには存在しない概念である。Jev は別のゲームについて尋ねられていたことになる。一方の Haiku には、ズーキーパー用に書いた「点を多く取れる手を選べ」という文が渡っていた。測定対象がスコアである以上、この非対称はそのまま結果に出る。加えて、レベルアップには全種のノルマが要るという最も重要な規則が、どちらにも伝わっていなかった。

対処として、目的を説明する文をゲーム側に一箇所だけ持たせ、両者へ同じ文字列を渡す構造に変えた。エージェント側のコードにはゲーム固有の戦略を書かない。この分離が崩れていないかは、エージェントの実装にゲーム固有の語が混ざっていないことを確認するテストで縛っている。

### ゲートウェイが無視する構造化出力

Haiku 側は当初、`output_config` に JSON Schema を渡して回答を候補ラベルの enum に固定していた。ところが 30 手すべてがパース失敗に終わっていた。

原因はゲートウェイの側にあった。`output_config` を付けたリクエストに対し、エラーを返さず 200 でスキーマを無視した応答が返っていた。中身は普通の散文である。

```
stop_reason: end_turn
text: "I'd be happy to help, but I don't see the options for A, B, and C..."
```

400 が返れば送信時点で気付けたはずで、200 で黙って無視される形が最も見つけにくい。現在は、まず JSON としてのパースを試し、失敗したら応答文からラベルだけを正規表現で拾う二段構えにしてある。

そのラベル抽出にも一度不具合があった。候補が 12 個あると `A` から `L` までのラベルが使われるため、文中の単語に含まれる大文字を拾ってしまう。「Looking at the options, I pick G」から `L` を、「Based on the quota, C is best」から `B` を取り出す実装になっていた。前後が英字でないラベルだけを対象にし、複数見つかったら最後のものを採る形に直した。モデルは候補を検討してから結論を書くので、最後に現れるラベルが答えである。

### 代打ちが成績を押し上げる

API 呼び出しが失敗した手は、評価式の最善手で代打ちして局を続ける設計にしている。局の途中で止めると 30 手が揃わないので、この設計自体は変えていない。問題は、全手が代打ちになった場合の成績の見え方にある。評価式との一致率は 100%、評価値の差は 0.00 になり、結果の表の上では最も優秀な行が出来上がる。それはヒューリスティックの成績であって、そのエージェントの成績ではない。

このリポジトリでは実際に 2 回、その形で誤ったデータを作りかけた。1 回目が前述の構造化出力の件で、30 手すべてが代打ちだった。2 回目は、Haiku をサブエージェント経由で動かしていたときにレート制限で応答が止まり、14 手中 8 手が代打ちになった局である。後者は `agreement 0.93 / mean_regret 0.04` という、表だけ見れば優秀な行として残っていた。

対処は 2 つある。代打ちした手数を結果の表に必ず出し、0 でない行は計測になっていないと判断できるようにした。さらに、2 手続けて応答が返らない場合は局ごと中止し、結果の行自体を出さないようにした。

### 候補手の説明に入っていた誤った手数

候補手の説明に付けている「この手を打ったあと何手打てるか」という値が、`moves left after 93` のように不自然に大きくなることがあった。予測値と実際の値の相関を取ると 0.069 で、ほぼ無相関だった。予測の平均が 41 手に対し、実際は 8.4 手である。

原因は 2 段階だった。候補手を評価するための盤面は補充なしで作るため、1 連鎖で処理が止まり、消え残りの並びが盤面に残る。そして合法手の判定を「盤面のどこかに 3 個以上の並びがあるか」で行っていたため、その消え残りのせいでほとんどのペアが合法手として数えられていた。判定を「入れ替えた 2 マス自身が並びを作るか」に変えたところ、相関は 0.900 になった。

この値は候補手の説明としてそのまま両モデルに渡している。評価式の内部が汚れていただけでなく、モデルに誤った情報を見せていたことになる。

## 一致率と regret を判断の質の指標にできない理由

計測を始めた当初は、評価式の最善手との一致率（`agreement`）と、選んだ手と最善手の評価値の差（`mean_regret`）を、判断の質の指標として使うつもりでいた。この 2 つは質の指標にならない。

ヒューリスティック単体は、定義上つねに一致率 100%、評価値の差 0.00 になる。評価式への追従度が質を表すのなら、この行が 30 手スコアでも 1 位になるはずである。実際には 3 者の真ん中（Jev 2,494 < ヒューリスティック 2,552 < Haiku 2,676）に位置していた。追従度の最大値と、スコアの最大値は一致しない。

この 2 つが測っているのは評価式との距離であって、最善手との距離ではない。評価式そのものが正解を与えるわけではないので、そこから離れた手が悪い手だとは限らない。結果の表には両方を今も出しているが、代打ちの有無を確認するための材料として見ている。

なお、レベル 2 に到達するまでの手数という別の指標でも比較していたが、その数値は Jev の質問文を直す前に取ったものである。直したあとに取り直せていないため、この記事からは外した。

## 判断の質の差はまだ測れていない

今回の計測で確認できたのは、同じ選択を同じ回数させたとき、System One のほうが 3.1 分の 1 の時間と 10.7 分の 1 の費用で済むという点である。選択肢をこちらで用意できる処理であれば、文章生成の能力に時間と費用を払う必要はない。

判断の質については、差があるともないとも言えていない。API を呼ばないヒューリスティックが両者の中間に収まった以上、この題材では最後の 1 手の選択がスコアにほとんど影響していない。候補の絞り込みを緩めるか局数を増やさないと、質の比較にはならない。

計測系を組むうえで学んだのは、エラーを出さない失敗を先に検知できるようにしておく必要がある、という点である。代打ちは局を止めないために要るが、その手数を表に出さなければ、ヒューリスティックの成績をモデルの成績として読んでしまう。指示文の非対称に至っては、指標をいくら整備しても検知できない。今回それに気付いたのは、録画した 1 局のスコア差への違和感からだった。
